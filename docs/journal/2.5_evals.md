# Evals Journal (a side project off Week 2)

Not part of the assigned Week 2 OpenTelemetry lesson (see
[`2_otel.md`](2_otel.md)) — this is a side project that grew out of it.
Coming off that tracing work, the natural next question was: now that the
agent is observable, how would I actually *evaluate* it — not just watch
one run happen, but score it, repeatably, across models? This is the story
of building that, and of everything that went sideways on the way to a
dashboard I actually trust.

## Starting point

The brainstorm started big — a full experiment-tracking platform alongside
Jaeger/Grafana, Prometheus metrics, exemplar links, the works. I scaled it
down on purpose: `week0_explore/explore_architecture/001_playing_agent`
already had four hand-run, human-graded test objectives in `AGENTS.md` (find
the bakery menu, train `kick`, find a starting guild, kill the Massive
Minotaur). Those were already evals in spirit, just graded by a human
reading a completion report instead of by code. The obvious first move was
to automate the easiest one — the bakery menu — with a deterministic,
file-existence check instead of an LLM judge, and build outward from there
only once that worked end to end.

`evals/bakery.py`'s scenario, `evals/boukensha_agent.py`'s subprocess
adapter, `evals/score.py`'s scorer, and `evals/run_bakery.py`'s runner came
together around `boukensha.run()` — no changes to the core agent needed for
the first pass, since `run()` already did everything a single trial needed.

## The first real trial was a legitimate failure, and that was the point

The first live run didn't pass. The `dummy` character logged in inside a
dark sewer maze — not the town square — spent its entire 25-action budget
bumping into "Alas, you cannot go that way..." in the dark, and stumbled
into an unplanned spider fight near the end. FAIL, 25/25 iterations, zero
output.

That was a good result, not a bad one: nothing in the harness broke, the
scorer correctly captured a clean process exit with no dispatch errors, and
the transcript explained exactly what happened. It's the whole reason to
build a harness instead of eyeballing runs — a failure you can *read* is
worth more than a pass you can't explain.

## Strict vs. reprompt

Wanting to see whether a model that runs out of budget can actually finish
given more room, versus one that's genuinely stuck, led to
`boukensha.run_reprompted()` — new in `boukensha/__init__.py`, giving the
agent a fresh iteration budget when it exhausts one without voluntarily
ending its turn. It isn't new behavior for the framework, just newly
available outside the REPL: `repl.run_turn()` already built a brand-new
`Agent` per turn (iteration counter reset, context/tools/the live MUD
session shared) every time you typed a follow-up message. `run_reprompted()`
is that same mechanism, minus the human typing the follow-up.

## Visualizing it — and staying out of Grafana

The dashboard went into `log_viz` (`/evals`, plus eval runs surfaced
directly on the main Sessions index) rather than into Grafana. Partly
practicality — Grafana only had Tempo wired up, and getting eval results in
front of it meant standing up a real metrics pipeline. But mostly it was
because `docs/plans/15_otel_tracing.md`'s own verdict on Jaeger and Tempo
was that neither trace UI clearly communicated the agent's decision-making
despite being technically correct — density without legibility. No reason
to inherit that problem for evals when `log_viz` already had a transcript
viewer that worked. The scatter chart (iterations vs. duration, colored by
pass/fail) is plain inline SVG, no chart library, same house style as the
existing token sparkline.

## Pitfalls, in the order they bit

- **Secrets almost leaked into eval output.** The first adapter version
  copied `.boukensha/.env` (API keys) into every run's throwaway config
  directory under `evals/results/`. Gitignore happened to already cover it
  (a bare `.env` pattern matches at any depth), so nothing was actually
  exposed — but "happened to be caught by an unrelated rule" isn't a plan.
  Fixed by never writing the key to disk at all: read into memory, passed
  straight into the subprocess's environment.
- **Two eval batches fighting over one MUD login.** Mid-session, a
  self-started `run_bakery.py` batch and a validation trial I'd kicked off
  in the background both tried to log in as `dummy` at the same time.
  CircleMUD only tolerates one live session per character — exactly the
  failure mode the README now warns about up front. Killed the redundant
  one as soon as it turned up in `ps`.
- **Ruby doesn't hot-reload.** `log_viz`'s `.erb` views reload on every
  request, but `app.rb`'s route/helper code only loads once at process
  start. Every time a new helper or route got added, the already-running
  server would render the *new* template calling a method that didn't
  exist yet in the *old* loaded code — three separate `NoMethodError`s
  before that pattern was fully internalized (`/evals`, then `/`, twice,
  the second time for `eval_results.rb` specifically, not just `app.rb`).
  Eventually fixed properly instead of just remembered around:
  `sinatra-contrib`'s `Sinatra::Reloader`, registered in development mode
  with `also_reload` pointed at every `.rb` file in `lib/log_viz/` (not
  just the main app file, which is all `register` tracks on its own —
  found that gap by testing the wrong file the first time and declaring
  victory too early). Verified live: added a method, hit the route with no
  restart, worked; reverted, hit it again, still worked.
- **The character saved itself into the bakery — then the general store,
  even after "fixing" it.** Some run called `save_character` while standing
  in the bakery. CircleMUD persists character position on save, so every
  trial after that logged in *already at the bakery* — a free pass on the
  navigation half of the task for every model that ran afterward. First
  fix: `evals/_driver.py` initially re-registered `save_character` as a no-op
  before every trial (`Registry.register_tool` just does `self.tools[name] =
  tool`, so re-registering the same name shadows the original — no
  core-package change needed), via the `block=` hook `run_reprompted()`
  already exposed for exactly this kind of caller-side override. The final
  version removes the tool from the registry entirely. Then it happened *again*
  — from the general store this time — with the block demonstrably active.
  Turned out the whole premise was wrong: I tested it directly (logged in,
  moved the character, killed the connection with no `quit` and no `save`
  at all) and reconnecting resumed instantly, mid-map, via CircleMUD's
  ordinary linkdead-resume ("You take over your own body, already in
  use!"). A clean `quit` doesn't reset it either — I checked that too.
  `save_character` was never the actual mechanism; CircleMUD keeps a
  disconnected character live in memory regardless of how the connection
  ends, save or no save. There's no `recall` command on this server either
  (`Huh!?!`), so there is no instant reset command. At this point in the
  investigation, walking the character back by hand was the only known
  reset. The later recovery task automated that same ordinary navigation;
  it still does not reset the wider character or world state.
  `save_character` stays blocked anyway (it still matters for making a room
  durable across an actual server restart), and every trial now logs a final
  `look` so at least there's no guessing where a batch left things.

- **A model wrote a bar's menu, called it done, and the scorer believed it.**
  A small model (`qwen3.5:4b`) couldn't find the bakery, wrote the *bar's*
  menu (ale, firebreather, a bottle of local specialty) to
  `data/mud_bakery.txt` instead, and — in its own final summary — explained
  it had substituted the bar because no bakery existed, while still
  reporting the task complete. The scorer's only check was "does the file
  exist and have content," so it scored a clean PASS. Genuinely funny, and
  a real gap: a non-empty file was never proof the *right* file got
  written. Fixed by checking content, not just existence — `evals/bakery.py`
  now carries the real bakery item names captured during the original
  manual playtest (`danish pastry`, `waybread`, `bread`), and `score.py`
  requires at least one to actually appear (case-insensitive) before
  counting a run as success. Still fully deterministic, no LLM judge: these
  are fixed, static game-world data, not something that varies run to run,
  so matching against the known real menu is a legitimate check rather than
  a fragile guess. A run that writes a wrong-but-plausible file now shows a
  distinct 🎭 marker in the dashboard instead of silently blending in with
  either a clean PASS or a no-file FAIL.

- **A recovery feature that looked built, tested, and shipped — and had
  never once actually worked.** Once `save_character` turned out not to
  fix drift (see above), the real answer was self-healing: on a room
  mismatch, run `return_to_midgaard.py` as a recovery trial before giving
  up, and only halt the batch if recovery itself fails. Built it, unit-
  tested the orchestration logic with mocks, shipped it. Then a real batch
  hit a room mismatch, the recovery agent successfully navigated Main
  Street → Market Square → Temple Square → The Temple Of Midgaard in five
  moves, said so explicitly in its own final response — and the batch
  still hard-stopped with "recovery failed." The bug: `_driver.py`
  computed the final `look` capture correctly, but the dict `_run_trial()`
  actually returns never included the `final_room` key at all — a plain
  omission, not a logic error. Every recovery attempt's own success check
  (`bool(recovery_result.get("final_room"))`) had been silently checking a
  key that was never there, since the day the feature was written. The
  synthetic dashboard tests that "validated" this only ever exercised
  fabricated JSON with `final_room` hand-filled in — the actual capture
  path, subprocess stdout parsing included, was never once run against a
  real trial before this. Fixed with one added line; the harder fix was
  noticing that "I tested it" had quietly meant "I tested the part that
  was easy to test."

- **Round two of the fabrication problem: a model that never even
  connected still wrote a whole invented menu.** `qwen3.6:35b-a3b`, every
  `mud_connect()` call timing out for an entire trial, wrote a complete
  fabricated bakery menu — "Dragon Bread," "Magic Leavened Loaf" — and
  reported success anyway, explaining the invention in its own summary.
  The keyword check passed it, because the fake menu happened to contain
  the word "bread," which was still in `EXPECTED_MENU_KEYWORDS` from the
  first fabrication incident. Two fixes: dropped the generic "bread"
  keyword (any bakery-themed invention contains it — it was never a real
  signal), then added a check with nothing to do with content at all. The
  first version required `mud_connect()` to have reported success in the
  session log. That turned out to be too narrow after the connector began
  auto-connecting before the agent's first turn: a successful automatic
  login emits no `mud_connect` tool event. The current scorer therefore
  accepts either a successful `mud_connect` result or any successful,
  guard-protected MUD action (`look`, `move`, `shop`, and so on). Those tools
  cannot return a non-error result unless the session is actually logged in.
  Keyword matching checks whether the output *looks* right; this connection
  evidence checks whether the agent was ever in a position to know what
  right looked like.

- **Chasing "why can't anything log in" led to a real bug two layers deep
  — and I nearly broke my own diagnosis by touching the shared MUD mid-
  batch, twice.** First self-inflicted collision: a stress-test script
  meant to reproduce a race condition kept running in the background and
  collided with the user's real batch — traced a `ConnectionError` back
  to my own leftover process. Second: ran a "quick" direct connectivity
  test without checking `ps` first, while a batch was mid-flight. Both
  fixed by checking for a running trial *before* touching the MUD, not
  after something breaks — a rule the harness now also enforces for
  itself (room mismatches trigger recovery; repeated connection/recovery
  stalls trip a bounded circuit breaker rather than letting the batch guess
  indefinitely). The actual root cause, once found without
  further collisions: CircleMUD logs showed a preflight check's connection
  still being force-killed by the real trial's own connect attempt six
  seconds later ("re-logged in ... disconnecting old socket") — and
  `mud.py`'s `mud_connect()` only calls `session.open()` if the socket
  isn't open *at all*. A socket left open-but-not-logged-in by one failed
  attempt gets handed straight back into another `login()` call, forever
  — every retry was hitting the exact same broken connection, not a fresh
  one, which is why it failed identically no matter how many times an
  agent tried. Looked like the MUD server degrading under load (it partly
  was, hence a container restart earlier); the part that made it
  *unrecoverable* within a trial was this. Fixed in `mud.py`, not in
  `evals/` — a framework bug, not an eval-harness one.

- **Local absolute paths were quietly baked into every result row.**
  `working_dir`/`log_path` in `results.jsonl` held the full local
  filesystem path — harmless in the sense of no real secret, but exactly
  the kind of machine fingerprint worth keeping out of committed data, and
  it came up in a pre-commit sweep the same way the two fabrication
  incidents did: something nobody would have caught by reading the code
  once. Fixed once, centrally, in `score.py`'s `score_run()` — the one
  function every eval runner already funnels through — rather than as a
  convention each new `run_*.py` script would have to remember: paths
  relative to `evals/results/` instead of a flat redacted placeholder, so
  the dashboard's transcript/story/trace links keep working while nothing
  machine-specific survives. Retroactively rewrote the existing rows to
  match rather than leaving old and new data inconsistent.

## How the connector and MUD state actually interact

The confusing part was the word “save,” which was being used for two
different kinds of persistence. An eval subprocess, its LLM conversation,
and its TCP connection can all be fresh while the game character is not.
The authoritative state belongs to CircleMUD.

```text
fresh eval subprocess
  → mud tools register and create one Session
  → Session opens one TCP socket and logs in as dummy
  → every MUD tool in that trial reuses that socket
  → subprocess ends and the socket closes
  → CircleMUD leaves dummy link-dead in the current room
  → the next fresh subprocess logs in as dummy
  → CircleMUD reconnects it to the same in-world body
```

That is why recovery and bakery do not need to share agent memory or a live
socket. They use separate subprocesses and connections, but authenticate as
the same server-side character. Recovery walks that character to the Temple,
disconnects, and the bakery trial reconnects to the body now standing there.

`save_character` is a separate durability mechanism. It writes character
state to the player files used after a real server restart; removing that
tool does not rewind the live character, evict a link-dead body, or teleport
it to its original load room. The Compose setup bind-mounts
`week0_explore/infrastructure/lib` into the container, so player files also
survive container replacement. A location written by an earlier save, clean
quit, autosave, or shutdown can therefore reappear after the server itself
starts again even if the current eval driver never exposes `save_character`.

The preflight check is another independent connection: connect, log in,
`look`, close, then wait briefly for CircleMUD to finish descriptor cleanup.
If the room is wrong, `run_once()` launches the return-to-Midgaard scenario;
if recovery's final `look` confirms the Temple, it launches the bakery
scenario. This normalizes position through gameplay, not through fixture
resetting. Health, movement, inventory, combat state, mobs, and other world
changes can still carry between trials, so the evaluation remains stateful
even when every bakery attempt begins in the intended room.

## Round two: the wall-clock confound, and finally watching it work

Everything above got the harness to a state where it was *usually* right.
The next overnight batch surfaced one more layer: a class of failure that
had nothing to do with the model, the scorer, or even CircleMUD's game
logic — the eval runner's own plumbing was quietly lying about what it was
testing.

- **A stale-socket guard that didn't match its own definition.**
  `Session.open()` refused to reopen if `self._socket` was merely truthy;
  `is_open()` (used everywhere else, including `mud_connect()`'s own
  close-before-reopen retry logic) also checked `self._closed`. After a
  passive disconnect, the reader thread sets `_closed = True` but can't
  safely null `_socket` itself — closing it from inside the thread it's
  running on would deadlock against `close()`'s own `join()`. So
  `is_open()` correctly said "not open," the retry logic skipped closing
  anything, and `open()` then raised `"already open"` off the stale
  reference alone. Every retry hit the identical wall. Fixed by making
  `open()`'s guard match `is_open()`'s real definition instead of
  reinventing a narrower one.

- **The actual root cause was twenty-year-old C, not this codebase.**
  Even after that fix, connections kept stalling unpredictably — sometimes
  past a client's login timeout, sometimes not. Docker logs showed
  `SYSERR: gethostbyaddr` on almost every reconnect. Reading tbaMUD's own
  source straight out of the running container (`docker exec circlemud`,
  the Dockerfile's multi-stage build happens to copy the full source tree
  into the final image, not just the compiled binary) found it:
  `new_descriptor()` in `comm.c` does a **blocking** reverse-DNS lookup on
  every single connection, on the single-threaded main game loop, unless
  `nameserver_is_slow` is set. Docker's bridge network has no usable
  reverse DNS for its own gateway IP, so every reconnect briefly froze the
  *entire server*, not just the connecting client — exactly the failure
  mode the eval harness's rapid reconnect cycle hits hardest of anyone who
  has ever played this MUD. Patched the default at Docker build time
  (`sed -i` on `config.c`, one line) instead of relying on a live CEDIT
  toggle that a container rebuild would silently undo. Zero
  `SYSERR: gethostbyaddr` lines since.

- **A results file that was being silently rewritten out from under a
  live process.** Mid-batch, `bakery.jsonl` stopped growing on disk even
  though the run_bakery.py process was still alive and still printing
  PASS/FAIL lines. `lsof` explained it: the process's file descriptor
  pointed at a `(deleted)` inode — something had done an atomic
  replace-via-rename on the file at that path (most likely this session's
  own VS Code extension host reacting to a mid-batch `git commit`), which
  orphans any file descriptor opened before the rename without touching
  it. Every row the batch wrote after that point was going into a file
  with no name, invisible to `tail`, invisible to the dashboard, and would
  have vanished entirely the moment the process exited. Recovered it
  live and without killing the batch first: Linux doesn't actually free a
  deleted file's contents while a process still holds it open, so
  `cat /proc/<pid>/fd/<fd>` read back everything that would otherwise have
  been lost. Merged the recovered rows in, then restarted the batch so its
  new process held a properly-linked handle. The standing rule now: nothing
  gets written or moved inside `evals/results/` while a batch is running —
  the directory is globbed wholesale by both `run_bakery.py`'s own append
  and `log_viz`'s dashboard, so anything else that touches a file there
  becomes a silent trap for whichever of them opened it first.

- **The wall clock was overriding the very budget it was supposed to be
  measuring.** `--timeout` had been sitting at a flat 300 seconds since
  the CLI flag was added, on the assumption that it was a generous outer
  bound around the agent's own iteration/token/reprompt limits. It wasn't.
  Measured against real trials: **28% of all bakery trials that night were
  killed by the wall clock**, not by the agent exhausting its own budget —
  killed trials averaged 14 of their allotted 25 iterations and 0 of their
  available reprompts used. Real per-iteration latency against a local
  Ollama backend ran a median of 6.6s and a 90th percentile of 11.2s;
  `reprompt2` alone promises up to 75 iterations (3 turns × 25), which at
  that pace can take several times the old flat timeout for a *single*
  trial. The fix wasn't a bigger flat number, it was removing the
  disconnect entirely: `run_bakery.py`'s `default_timeout()` now scales
  off `--reprompts` and the scenario's own `MAX_TURNS`, so the agent's own
  design — not an unrelated guess about how long that should take — is
  what actually decides when a trial is over.

- **Two smaller layers of the same idea, both about not losing a whole
  night to one bad moment.** A single failed recovery attempt now gets one
  retry with a fresh connection before being called a real failure (the
  exact class of hiccup the socket-guard bug above caused looked
  indistinguishable from a genuinely stuck character until it was traced
  down). And a batch no longer hard-stops on the first stalled repetition
  at all — it logs the stall, backs off, and tries the next repetition,
  which gets its own fresh preflight and recovery attempt; only three
  stalls *in a row*, with no successful trial in between, actually stops
  the batch. That specific pattern — not one bad trial — is what actually
  distinguishes "something structural is broken" from "the MUD had a rough
  minute."

None of this was visible from inside a single trial's transcript. Every
one of these bugs looked, from the model's point of view, like "the MUD
isn't responding" — which was true, just not for any reason the agent
could have done anything about.

## Midgaard and the bakery, finally passing together

The payoff showed up as an ordinary-looking batch entry, `qwen3.6:27b`,
`reprompt2`: `return_to_midgaard` PASS in 101.7 seconds, followed
immediately by a real `bakery` PASS in the same repetition slot. Small
thing to say out loud, but it was the first time all of it — drift
detection, the recovery task actually navigating home, the real scenario
then running clean against a correctly-positioned character — had
happened back to back, for real, unassisted, since the recovery feature
was first written. Every earlier "success" in that path had either been a
mocked test of the orchestration logic, or a real recovery that the
`final_room` key bug (see above) silently reported as failed anyway.

It held up under repetition after that, not just once: further batches
showed multiple further recovery passes, and rescoring the historical data
against the fixed `mud_connected` check (the auto-connect blind spot from
the second fabrication incident, above) turned up **six more genuine
recovery passes** that had been sitting in the results file mis-scored as
failures the whole time — real successful navigations, reported as FAIL
because the check for "did this actually work" had a gap, not because
anything had actually gone wrong. The three sewer-stuck ones from that
same stretch stayed FAIL on rescoring, correctly — a maze with no light
source is still a maze, and self-healing was never meant to make every
recovery attempt succeed, only to give a stuck run a real shot instead of
none.

With the DNS stall, the socket guard, and the timeout sizing all fixed at
once, the harness stopped being the thing under test by accident. What's
left in a FAIL now is much closer to actual task difficulty — a model
that connects fine, has the time it needs, and still can't find the
bakery or word-for-word repeats a wrong tool choice — which is the
question the eval was supposed to be answering in the first place.

## Extending the harness once it could be trusted

Once a batch could run overnight without the environment itself being the
main source of failure, the harness became worth pointing at agents other
than boukensha. Two additions, both scored through the exact same
`task_success`/`mud_connected`/content-match contract so results sit
side by side with everything above:

- **An OpenRouter backend** (`boukensha/backends/openrouter.py`) — the
  classic OpenAI `/v1/chat/completions` schema (not the `/v1/responses`
  API `openai.py` already speaks), accepting any `vendor/model` slug
  without requiring the usual per-backend `MODELS` whitelist, since
  OpenRouter's own catalog is far too large to enumerate ahead of time.
- **An OpenCode integration** (`evals/run_bakery_opencode.py`,
  `score_opencode.py`, a new purpose-built `.opencode/agents/
  bakery-evaluator.md`) — driving the `opencode` CLI non-interactively
  through the identical bakery task, reusing the preweek exploration's
  tmux+telnet MUD bridge rather than building a second one. Both agents
  share the one live MUD account CircleMUD allows a single session for,
  so the runner explicitly tears its tmux session down after every trial —
  a session left alive would otherwise sit on the character indefinitely
  and collide with the next boukensha batch, the same category of mistake
  the very first pitfall in this journal was about, just with a different
  agent this time.

## 2026-08-04 — Installed is not tool-capable, and tool-capable is not agent-capable

Ollama model selection had another hidden confound: Boukensha's backend treated
its small static `MODELS` metadata table as an allowlist. Most models installed
on the configured server were rejected before Ollama saw the request, while at
least one allowlisted model (`gemma2:27b`) did not advertise Ollama's `tools`
capability at all. The table was simultaneously excluding potentially valid
models and admitting a model that the runtime said was incompatible.

The eval runner now discovers `/api/tags`, inspects `/api/show` capabilities,
deduplicates aliases by digest, and can select all tool-advertising completion
models without embedding the private server address. The static backend table
is metadata only; unknown tags use conservative context accounting and Ollama
decides whether they exist.

That still does not make `capabilities: [tools]` an eval result. Prior Gemma
runs appeared to get stuck around tool calls despite some Gemma tags supporting
them. A new optional two-request probe therefore tests both halves of the
contract: emit one exact tool call, then consume its result and return a final
completion without calling again. This separates `no_tool_call`, malformed
arguments, repeated `tool_loop`, and missing final completion before a model is
given an expensive stateful MUD trial. On the inspected server, Gemma 2 tags do
not advertise tools and are filtered; Gemma 4 tags do and must still prove the
round trip. Passing the probe means only that the minimal harness protocol
works, not that the model can choose among Boukensha's full toolset or navigate
the game.

This is the same eval lesson in a new form: a nearby proxy (installed model,
advertised capability, first successful tool call) must not silently stand in
for the behavior actually being tested (a reliable multi-turn agent loop).

## Main lesson

Three confounds now, and each one took a wrong first fix before the real one.

The environment confound: the dangerous thing was never the model, it was
the shared, stateful fixture being tested against. The instinct was to
blame the agent ("it called `save_character`, block that") when the real
cause was the environment itself quietly persisting state on every
disconnect, agent action or not. The lesson isn't "prevent the agent from
saving" — it's "assume a shared, stateful eval environment leaves a mark on
its own, verify how, and don't stop investigating at the first plausible
mechanism that happens to involve the thing under test."

The scoring confound: "the file exists" was standing in for "the task
succeeded," and the gap between those two only became visible when a model
was honest, in its own output, about having failed the real objective while
the harness scored it a pass anyway. A deterministic check is only as
trustworthy as what it actually verifies — existence is not content, and a
model with the right words but the wrong facts is a normal, not a rare,
failure mode. Same root instinct as the environment confound: check what
actually happened, not what's easiest to observe. It recurred: the same
model, later, wrote a menu without ever connecting at all, and the fix had
to move from "does the content look right" to "did the agent ever have a
way to know" — the first fix narrowed the gap, it didn't close it.

The validation confound, and the newest one: the recovery feature's own
success check was broken from the day it was written, and nothing caught
it because "tested" had quietly narrowed to "the parts that were easy to
mock." A unit test on the orchestration logic and a synthetic dashboard
render both passed, and both were real tests — they just didn't touch the
one line that mattered, the actual dict key connecting a real subprocess's
real output to the check that decided pass or fail. The lesson isn't
"write more tests," it's that a passing test suite answers exactly the
question it was pointed at and no other — a feature isn't verified until
something has watched it work end to end, against the real thing, at least
once. Everything upstream of that line was correctly built and still added
up to silent, permanent failure.

The infrastructure confound, and the one that took longest to see because
it never once produced an error that pointed at itself: a blocking DNS
call in twenty-year-old C code and a flat timeout sized by guesswork were
both, quietly, part of what was being measured. Every prior confound was
at least visible from inside a trial — a wrong file, a broken check, a
character in the wrong room. This one wasn't. A trial killed by the wall
clock at 300 seconds and a trial that genuinely couldn't finish in time
produce an identical FAIL, and nothing in the transcript tells you which
happened — the same instinct that caused the first fabrication incident
("the file exists, so it passed") was waiting one layer further down
("the trial failed, so the model failed"). The fix wasn't smarter scoring
