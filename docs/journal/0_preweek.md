## What 001 Uncovered

The first experiment showed that the coding-agent harness could operate the MUD, but only after the terminal connection was treated as persistent state. Codex 5.6 Sol succeeded with a persistent PTY, while Qwen 3.6 succeeded with a long-lived `tmux` session and a helper that sent one command at a time. Qwen 3.5's short-lived `nc` pipelines timed out, and Qwen3-Coder:30B struggled to complete its tool calls.

This made the connection layer as important as the model. The MUD login is an interactive protocol with timing-sensitive prompts, so a one-shot shell command is a poor abstraction even when the model understands the goal.

## What 002 Uncovered

Agent Skills provided a useful way to extract the successful behavior into a reusable capability. The `play-mud` skill now tells an agent to reuse an existing persistent session, read full game output, confirm facts from direct evidence, recover from errors, and keep scripts in a predictable location. The skill generated by a specialist model was a starting point rather than a finished solution; the experiment still required human review and several rounds of task-specific refinement.

Tests 2 and 3 showed that Qwen 3.6 could go beyond a fixed navigation task. It initiated combat with `kick <target>`, defeated a beastly fido, and earned experience. It also identified Dummy as a level 3 Sentress, found the Guild of Swordsmen, mapped its interior, and located the guildmaster in the Tournament and Practice Yard.

Test 4 revealed the limits of that success. On a longer objective, the agent accumulated useful world knowledge but lost precision around state. Its notes had to explicitly reject invented or unsupported details such as the name `dummydummy`, level 127, an unconfirmed room title, and claims that had not been verified from game output. This led to a stricter checkpoint protocol: update the player state, world knowledge, and current report after no more than four MUD commands, checkpoint immediately after meaningful changes, and read the files back before continuing.

Qwen 3.6 has also suddenly begun struggling with the login flow again, despite previously completing it with a persistent-session approach. In one Test 4 attempt, it spent so much of its output budget on login and exploration that it reached the maximum token limit while narrating a checkpoint, before writing the discovery to the memory files. That regression is significant: success on one run did not establish reliable operation, and describing a planned checkpoint did not protect the state. The operating instructions now prefer `telnet` over `nc` and require the agent to perform and verify memory writes before narrating a checkpoint. The current Test 4 report remains in progress, and neither the Newbie Training area nor the Massive Minotaur objective has been completed.

## Main Lesson

The model was only one part of the agent architecture. Stateful environments such as MUDs require a reliable connection layer, explicit memory discipline, frequent evidence-based checkpoints, and recovery from interrupted or mistimed interactions.

The renewed Qwen 3.6 login failures emphasize that a general coding agent may not be the best fit for this task. Coding agents are optimized around discrete shell commands and file edits, while a MUD requires continuous, timing-sensitive interaction with a live session. Agent instructions and skills can improve performance, but they cannot fully compensate for a mismatched interface or guarantee consistency across runs. A dedicated MUD client, protocol-aware adapter, or purpose-built gameplay agent would likely be a more dependable foundation, with the language model focused on planning and decisions rather than terminal-session management.
