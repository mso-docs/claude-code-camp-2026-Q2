# Exploring Agent Architecture

Today I compared several coding agents on the same tbaMUD task. Each agent received repository instructions telling it to log in as Dummy, identify the movement commands, find the bakery, save its menu, and update the player and world memory files.

The local models ran through Ollama with Pi as the coding harness. I also ran the task with Codex so I could compare how each agent handled the same stateful terminal workflow.

## Initial Assessment

This experiment tested whether a general-purpose coding agent could operate a stateful MUD through terminal tools alone. The agents were asked to follow repository instructions, log in, explore Midgaard, locate the bakery, and save the bakery menu.

### Observations

- The coding agent created temporary scripts to manage the socket connection.
- The agent struggled with the deterministic MUD login flow.
- The agent read unrelated repository files and used tool calls.
- Increasing the model intelligence did not resolve the core connection issue.
- The agent had poor visibility into its failed login attempts.

### Technical Conclusion

A coding harness alone is not a good fit for operating the MUD.

The deterministic login and connection flow should be handled by a reusable MUD SDK rather than regenerated by the model on every attempt.

A specialized agent loop, potentially using an MCP server connected to the MUD SDK, would provide better reliability, visibility, and token efficiency.

## What Happened

- **Qwen 3.5** repeatedly tried to send the login sequence through short-lived shell commands. It never completed the login and eventually timed out.
- **Qwen3-Coder:30B** found the agent instructions but ran into tool-call problems before completing the task.
- **Codex 5.6 Sol** waited for each login prompt through a persistent terminal session, entered the game, explored Midgaard, found the bakery, and saved the menu.
- **Qwen 3.6** created a helper script around a persistent `tmux` session. With that bridge in place, it also logged in, moved between the bakery, Main Street, and Market Square, and completed the task.

The detailed outcomes and completion reports are recorded in the [agent progress comparison](journal/0_preweek/agent-results.md).

## What I Learned

- The difficult part was not understanding the goal. It was preserving one connection while waiting for several server prompts.
- Piping a complete login file into `nc` was unreliable because the MUD performs client detection before asking for the character name.
- A coding agent's Bash tool may be designed around individual commands, while a MUD expects a long-running interactive client.
- A larger or more capable model did not automatically fix the mismatch between those two interfaces.
- The successful agents both gained a persistent terminal abstraction: Codex used a PTY, while Qwen 3.6 used `tmux`.
- Saving state in `data/player.md` and `data/world.md` made the agent's progress easier to inspect and reuse.

## What I Would Build Next

I would move the deterministic connection work out of the model's prompt and into a reusable MUD integration. That layer would handle client detection, login prompts, the persistent socket, response capture, and clean disconnection.

The agent would receive a small set of explicit operations such as:

- Connect or reconnect to the current character.
- Send one MUD command and return the complete response.
- Read the current room and exits.
- Save structured player and world state.
- Close the session cleanly.

This could be exposed as an SDK, a custom Pi tool, or an MCP server. The model could then focus on navigation and decisions instead of repeatedly rebuilding terminal-control code.
